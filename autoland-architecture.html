Section 01

Technical Context: How Jito and Writable Accounts Work

Solana's parallel engine handles separate state paths, but execution clashes when transactions compete to write to the same account. Jito coordinates this off-chain using the following steps:
01

Bundle Account Locking

Jito's BundleAccountLocker analyzes incoming bundle payloads to extract and lock the combined read/write accounts required by all transactions, securing exclusive, block-wide atomicity.

02

Conflict Set Grouping

Bundles requesting overlapping locks (e.g. trading bots competing for the same DLMM pool, token launch pool, or liquidating account) are isolated together into a Conflict Set.

03

Localized Auctions

Since only one conflict bundle can execute sequentially, Jito runs a localized priority auction. Bundles are ranked by their Priority Score; the highest score lands, while conflicting underbids are dropped.

Visualizing the Conflict Set Grouping Path
Key Insight: Standard RPC submission broadcasting to public mempools leaves your transactions open to sandwich attacks and leader-level sorting drops. AutoLand routes bypass this entirely via private Jito channels.
Section 02

The Jito Auction Model: Denominator Optimization

Inside a Jito Conflict Set, bundles are sorted using a structured Priority Score (effective tip density per compute unit requested) rather than absolute tip values:
Priority Score = Total Jito Tip (lamports) ÷ Sum of Compute Units Requested (CUs)
Transaction A (AutoLand Optimized)
Requested Compute: 50,000 CUs
Jito Tip: 5,000,000 lamports (0.005 SOL)
Effective Priority Score: 100 lamports/CU
STATUS: LANDED FIRST
Transaction B (Default Unoptimized)
Requested Compute: 1,400,000 CUs (Default)
Jito Tip: 70,000,000 lamports (0.070 SOL)
Effective Priority Score: 50 lamports/CU
STATUS: DROPPED / OUTBID

Because Transaction B requested standard unoptimized CUs, its priority density is halved despite paying a 14x higher absolute tip. AutoLand's CU resizing directly optimizes this denominator to win auctions cost-efficiently.

Section 03

Our Solution: Real-Time Contention Engine

AutoLand builds an active bidding profile for target accounts by parsing live gRPC transaction streams, scaling tips to outbid competitors during fee wars and falling back to global Jito fee percentiles (p50/p90/p99) when quiet.
Dynamic Telemetry Bidding & Execution System
Dual-Tiered Bidding Decision Logic

1. Telemetry Stream

Establishes a live Yellowstone gRPC subscription that pushes every transaction writing to the target account. This enables instantaneous competition mapping.

2. CU Resizing

Runs local pre-flight simulations. Replaces default compute unit request envelopes with actual consumption parameters (+10% safety margin).

3. Dual-Tiered Bidding

Under active pool contention, scales the Jito tip to outbid competitor rates. Reverts automatically to baseline global percentiles when the pool is quiet.

4. LLM Advisor

A closed-loop diagnostic engine (compatible with any fast LLM endpoint) that resolves drops, stale blockhashes, and rejections within strict programmatic safety caps.

Event-Emitter Telemetry Hooks

To support zero-overhead dashboards, UI monitors, and metrics monitoring (e.g. Grafana, Prometheus) without blocking the critical transaction submission path, the AutoLand class extends Node's EventEmitter. Operators can register listeners to capture:

  • telemetry_update: Emitted every 400ms with congestion levels, alpha contention, and next leader slot schedules.
  • bundle_submitted: Dispatched immediately upon forwarding to regional Jito Block Engines.
  • bundle_accepted / processed / finalized: Emits transaction state transitions resolved by Yellowstone gRPC confirmation filters.
  • ai_decision: Emits LLM Advisor diagnostics, selected recovery path (RETRY, HOLD, ABORT, FALLBACK_RPC), and parameter adjustments.

Section 06

README Questions & Operational Insights

Operational findings answering the core Solana network questions asked during mainnet runs:

Q1: processed_at vs confirmed_at Delta

Measures the consensus vote propagation latency across the validator network.

  • Optimal Network State: Delta sits at 400–800 ms (1–2 slots).
  • Degraded Network State: Latency spikes above 2+ seconds due to transaction congestions or micro-forking.
  • SDK Action: AutoLand dynamically scales backpressure delays to defer sub-sequent submissions until consensus stabilizes.

Q2: Why Avoid Finalized Blockhashes

Solana blockhashes are valid for exactly 150 slots (~60 seconds). Finalized status requires 32 slots (~13–15 seconds).

  • Validity Loss: A finalized blockhash burns 20–25% of its lifespan before the transaction is signed.
  • Staleness Risk: Congested blocks stretch slot times, causing finalized hashes to fail validation on arrival.
  • SDK Action: The stack queries blockhashes strictly at confirmed commitment to preserve the maximum execution window.

Q3: What Happens if a Jito Leader Skips their Slot?

Because Jito bundles are not gossiped across the public P2P mempool, they route off-chain to a specific scheduled validator. If that validator skips their slot, the block engine drops the bundle immediately.

  • Leader Distance Tracking: AutoLand tracks scheduled leaders via LeaderWindowDetector and holds dispatch if the slot window is unfavorable.
  • Multi-Region Broadcast: dispatches bundles to regional Jito Block Engines in parallel to mitigate routing drops.
  • AI advisor Intervention: If a drop is flagged, the AI Advisor immediately updates the blockhash and tip for the next viable window.
