Section 01 — Technical context

How Jito and writable accounts actually work.

Solana's parallel engine handles separate state paths, but execution clashes when transactions compete to write to the same account. Jito coordinates this off-chain in three steps.

01

Bundle account locking

Jito's BundleAccountLocker extracts and locks all read/write accounts across a bundle, securing block-wide atomicity.

02

Conflict set grouping

Bundles requesting overlapping locks — trading bots competing for the same DLMM pool — are isolated into a Conflict Set.

03

Localized auctions

Only one conflicting bundle lands. Jito runs an off-chain priority auction; the top Priority Score wins.

Section 02 — The auction

Denominator optimization wins auctions.

Inside a Jito Conflict Set, bundles are ranked by Priority Score — tip density per compute unit — not absolute tip.

Priority Score = Total Jito Tip (lamports) ÷ Compute Units Requested

Telemetry

Leader schedule

Dual bidding

Diagnoses drops, stale hashes, retries.

Commitment

Feature · Multi-channel routing options

AutoLand Options: Normal vs. High Urgency

Developers can specify transaction urgency in AutoLand submit options. This guarantees cost-effective execution paths depending on the context:

[SDK] autoland-urgency-options.tstypescript
// Example 1: High Urgency transaction (DLMM rebalancing, arbitrage, liquidations)
const highResult = await autoland.submit(rebalanceTx, {
  urgency: "high" // Routes to the private Jito block engine stack with dynamic tip outbidding
});

// Example 2: Normal Urgency transaction (Standard token transfers, admin tasks, fee collections)
const normalResult = await autoland.submit(transferTx, {
  urgency: "normal" // Bypasses Jito tips entirely; dispatched directly to standard public RPC nodes
});

Urgency: "normal"

Jito Bidding Stack

Target Transaction TypeHigh-contention events (e.g. liquidations, HFTs, mints)
Bypasses Jito TipNo (dynamic bidding via telemetry)
Routing ChannelPrivate block engine channels (Jito Bundles)

MAX LANDING PROBABILITY
Why this dual routing is critical: Liquidations, IDOs, and DLMM pool rebalances must land in a specific slot or they expire/get frontrun. Normal transactions (like transferring fees out of the bot or executing standard administrative commands) do not require microsecond-level speed. Forcing simple actions through the private Jito bundle stack would unnecessarily waste Jito tips, while sending high-contention actions to the public mempool would result in transaction drops and MEV exploitation.

Section 05 — Operational insights

Field notes from mainnet.

Answers to the network-level questions that surface during real contention runs.

Measures consensus vote propagation across the validator network.
  • Optimal: 400–800 ms (1–2 slots).
  • Degraded: 2+ seconds under congestion or micro-forks.
  • SDK action: AutoLand scales backpressure delays until consensus stabilizes.
Blockhashes are valid for 150 slots (~60s); finalized status takes ~13–15s.
  • Validity loss: a finalized hash burns 20–25% of its lifespan before signing.
  • Staleness risk: congested slots stretch time; finalized hashes fail on arrival.
  • SDK action: queries blockhashes at confirmed to preserve maximum window.
Jito bundles route off-chain to a specific validator. Skipped slot = dropped bundle.
  • Leader tracking: LeaderWindowDetector holds dispatch if the window is unfavorable.
  • Multi-region: dispatch to regional block engines in parallel to mitigate routing drops.
  • AI advisor: updates blockhash and tip immediately for the next viable window.
During high-congestion spikes, Jito's public Block Engine silently throttles and drops unauthenticated searcher bundle submissions.
  • Rate limit throttling: Anonymous submissions hit strict quota blocks during transaction wars.
  • SDK action: Integrates authenticated Jito UUID keys inside our RPC client, elevating the quota to a guaranteed 2 req/s.
If the AI Advisor takes longer than a block time (~400ms) to diagnose a failure, incoming slot events can trigger parallel loops, overwriting states and silently dropping retries.
  • Concurrency hazard: "Return early if busy" logic in retry loops results in dropping the most important transaction signals.
  • SDK action: Implemented a thread-safe locked queue semaphore. New failure events are queued and drained sequentially once the active advisor loop completes.
